## 1. 改动本身（`hooks/register.tsx:716-729`）

```ts
const comforting = await locked(async () => {
  if (!(await reallyWorried($, now)) || (await read($, moodComforted))) return false
  await update($, moodComforted, () => true)
  return true
})
```

**读代码**：

- `locked` 是对话内的 Promise 链（`:407-411`），后到的那次要等先到的那次回调结束才会开始，所以第二次摸头读到的标记一定已经是 `true`。
- 文件里的规矩是"不要在 `locked` 里再调用 `locked` 函数，会等自己"（`:405`）。新回调里只调用了 `reallyWorried`、`read`、`update`（都只读写 atom，没有再进 `locked`）；`react` 本身只被两个按钮的 `onPress` 调用（`:1408-1409`），不在任何锁里。没有死锁路径。
- `now` 是在进锁之前取的，后到的摸头用的是它自己点击时的时间，不是等锁之后的时间。担心的 5 分钟边界差几毫秒，无实际影响。
- 这个标记（`moodComforted`）是对话内的 atom，不是共享存档，所以不涉及跨对话的读写问题。
- 摸头用的另一把锁（`takePatLocked`）仍然在后面单独拿一次，两把锁不嵌套。

**实际运行**（探针，临时目录）：

| 场景 | v0.5.1 | v0.5.2 |
|---|---|---|
| `comforts` 预置 3，她担心时同时发两次摸头 | 计 2 次，解锁（错） | 计 1 次，未解锁 |
| 同上，同时发三次 | 计 3 次，解锁（错） | 计 1 次，未解锁 |
| 接着下一次担心里再摸一次 | — | 第 5 次，解锁 |
| 她的担心已经过去（6 分钟后）摸一次，`comforts` 预置 4 | 不解锁 | 不解锁 |

### P5-1（低）"是不是真的在担心"没有测试

- **位置**：`hooks/register.tsx:723`（`!(await reallyWorried($, now))`）；测试 `pet.test.ts` 里 `comfort:` 开头的 4 个用例。
- **场景**：把这个条件删掉，那么**她不担心时**的第一次摸头也会算安慰（标记初始是 `false`，担心结束后下一次担心之前也是 `false`），之后标记变 `true`，才不再继续计。现有的"她不担心时摸头不算"那条测试（`:948`）是连摸 5 次，只有第一次会算 1 次，达不到 5，所以放过去了。
- **验证**【实际运行】：变异 d 用我的"担心过去 6 分钟后摸一次，`comforts` 预置 4，断言**不**解锁"的测试一跑就失败；同一条测试在真实的 v0.5.2 上通过。
- **建议加的测试**（预期值是我跑过的）：

  再加一条"她从没担心过，只摸一次，`comforts` 预置 4，不解锁"也会抓住变异 d，这条我**没有单独跑**（推断：变异 d 下第一次摸头会把 `comforts` 变成 5 而解锁）。

### P5-2（提示）新测试看不出锁的范围

- 变异 b（检查在锁里、标记在锁外）在测试环境里也全部通过。原因是 atom 的写入是同步的：先到的摸头从锁里出来后，马上写标记，后到的摸头的回调才开始。
- 这说明新测试能抓住"没有锁"这个具体的错，但抓不住"锁的范围不对"。你现在的写法（全在锁里）是更稳的，我没有要求改。真实宿主里 atom 的写入是不是同步，我没验证。
