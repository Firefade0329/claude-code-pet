# 好感度与成就经济模型：模拟与审查

> 范围：`hooks/register.tsx`（v0.3.1，构建时间见 `/pet version`）里的好感度（affection）和成就（achievement）数值。
> 方法：先通读代码把规则读出来，再用 `affection_sim.py` 逐事件模拟。没有改任何代码。
> 标记：**已确认** = 我读了代码，或用脚本算过；**未验证** = 推断，或要在真实 Claude Code 里才能确认；**假设** = 用户行为的设定，不是代码里的事实。

## 结论（先看这个）

1. **认真使用的人（每天 30 轮对话、摸头 5 次、天天打开、偶尔番茄钟）：第 5 天到 Lv.7（朋友阶段），第 18 天到 Lv.14（家人阶段），第 35 天满级。**
   轻度（每天 5 轮、每周 4 天）是 29 / 116 / 233 天；重度（每天 100 轮、番茄钟 3 个）是 2 / 7 / 13 天。（已确认：代码 + 模拟；用户行为是假设）
2. **对话每轮 +1 点、没有每日上限，是最大的点数来源**：到满级为止占 42%（轻度）～ 80%（重度）。同样是"点一下就加分"的摸头有每天 5 次的上限，对话和番茄钟没有。每天 500 轮的话 4 天满级。（已确认）
3. **38 个成就的奖励总和是 213 点，只占满级所需 1603 点的 13.3%。** 实际到满级时只拿到其中 67～110 点（4%～7% 的收入），所以成就几乎不影响升级速度；而且一半以上的成就奖励（103～146 点）是满级之后才拿得到的，那时好感度已经没有用处。（已确认）
4. **没有"几乎升不动"的区间，也没有"升得太快"的区间——但两端都有问题**：轻度用户最后 7 级每级要 14～22 天；重度用户第 1 天就升到 Lv.5、第 2 天到 Lv.7。（已确认，用户行为是假设）
5. **连续天数没有宽限**：漏一天就从 3 点重新开始；只用工作日的人最长连续 5 天，`str7 / str14 / str30 / str100`（共 41 点）和"全部收集"永远拿不到。（已确认）

问题统计：高 0 / 中 3 / 低 3（见"发现的问题"）。

## 4. 发现的问题

### B-1　对话每轮 +1 且无每日上限（中）　【已确认】

- 位置：`hooks/register.tsx:1011`（`addAffection($, 1)`）；对照 `:81` 和 `:586` 的摸头每日上限。
- 场景：每天 100 轮的人 13 天满级，每天 500 轮的人 4 天满级。对话占满级点数的 42%（轻度）～ 80%（重度）。摸头和签到的上限让它们只占 4%–25% 和 6%–29%，所以升级速度几乎只由"每天聊多少轮"决定。自动化脚本、很短的提问、反复"继续"都按 1 点算。
- 建议：对话也设每日上限，沿用摸头的做法。例如"每天前 20 轮每轮 1 点，之后每轮 0.2 点"（方案 C）：认真用户 35→42 天，重度 13→27 天，每天 500 轮 4→12 天，轻度、普通完全不变（见 §5）。
- 未验证：`claude -p` 这类无界面模式下 hooks 是否触发，决定了"脚本刷分"是否真的可行。

### B-2　升级节奏偏快，长线成就的奖励在满级后才到手（中）　【已确认；节奏是否"偏快"是设计判断】

- 位置：`register.tsx:102-104`（门槛）、`:315-354`（成就表）。
- 场景：认真用户第 5 天就进入"朋友"阶段（Lv.7）、第 35 天满级；而 `t3000`（第 100 天）、`str100`（第 100 天）、`foc50`（第 100 天）、`pat500`（第 100 天）等长线成就都在满级之后。满级时认真用户只拿到 213 点奖励里的 110 点，剩下 103 点（48%）满级后才拿到，那时好感度已经没有用。重度用户满级时 24/38 个成就已解锁。
- 建议（二选一，取决于你想要的节奏）：① 整体放大门槛，例如叠加方案 D（门槛 ×1.5，认真用户 64 天满级）；② 长线成就的奖励别再发好感度，改成称号、台词或姿势之类满级后仍有意义的东西。
- 说明：我只能指出"满级前后分布不均"这个事实，"多少天才算合适"是你的设计决定，所以这里不给唯一答案。

### B-3　阶段切换点位置不均匀（低）　【已确认；设计意见】

- 位置：`register.tsx:111`（`stageOf`：Lv.6 / Lv.13 为界）。
- 场景：Lv.7 门槛是 201 点，只占满级点数的 12.5%，"主仆"阶段认真用户 4～5 天就过完；而 Lv.14（809 点，50%）对轻度用户要 116 天（约 4 个月），他们大概率一直看不到"家人"阶段的台词和 `up2` 姿势。
- 建议：如果希望"主仆"阶段持续更久，可以把阶段边界后移（如 Lv.9 / Lv.15）；如果希望轻度用户也能看到家人阶段，可以降低 Lv.14 的点数占比。

### B-4　连续天数没有宽限（中）　【已确认】

- 位置：`register.tsx:731-735`（`dayBefore`）、`:759-760`（`k.last === dayBefore(now) ? k.n + 1 : 1`）、`:324-328`（`str*` 成就）。
- 场景：漏一天，连续天数回到 1，签到奖励从 8 掉到 3。只用工作日的人每周一都重新从 3 点开始，签到平均每天 5 点（天天用的人是 8）；最长连续 5 天，`str7 / str14 / str30 / str100`（5+6+10+20 = 41 点）和依赖它们的"全部收集"（10 点）永远拿不到。
- 建议：允许 1 天宽限（连续天数在漏 1 天时不清零、只是当天不加），或把"连续 N 天"改成"累计 N 天"。
- 副作用提醒：加宽限要同步改 `dailyCheck` 与对应测试。

### B-5　摸头 / 戳一下的成就没有冷却，可以连点刷出来（低）　【已确认】

- 位置：`register.tsx:586-592`（超过 5 次后仍 `bumpStats({ pats: 1 })`）、`:594-598`（戳一下）、`:334-337`（`pat50 / pat200 / pat500 / poke50`）。
- 场景：点击没有冷却，500 次点击在一两分钟内就能点完，`pat500`（+10）等四个成就共 22 点直接到手，摸头的每日上限对成就不起作用。
- 建议：成就用的计数也按"每天只计前 N 次"，或给点击加最短间隔（比如 1 秒）。
- 严重度低：奖励合计只有 22 点，且只是自己和自己玩。
- 未验证：按钮有没有界面层的防抖（代码里看不到，真实点击速度没试过）。

### B-6　成就奖励相对升级太小，几乎不影响升级（低）　【已确认；可能是有意的设计】

- 位置：`register.tsx:315-354`。
- 场景：单个成就 2～20 点，只占满级的 0.1%～1.2%；到满级时成就只贡献 4%～7%。玩家看到"+10♥"，但对等级几乎没有感觉。
- 建议：如果成就只想当"纪念"，现状可以保留；如果想让成就有分量，可以把奖励按等级尺度放大 3～5 倍（注意会让满级更快，需要配合 B-1 / B-2 一起调）。

## 6. 局限

- 模型按"每天固定轮数"算，真实使用波动很大；表里的天数是量级参考，不是预测。
- 小成就（出错、压缩、过夜、5H 冲高、戳醒等）按期望值估计，解锁日可能偏早或偏晚几十天，但它们总共只占奖励的一小部分。
- 没有模拟同一台电脑多个对话同时运行，也没有模拟时区变化、夏令时、电脑休眠（这些放在代码审查 `code-review.md` 里）。
- 模拟里每个番茄钟都当作"走满 25 分钟"；真实中途放弃的不计分（`register.tsx:679-684`），这里没有建模。
