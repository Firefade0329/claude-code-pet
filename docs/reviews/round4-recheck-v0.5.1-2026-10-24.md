## 1. 迁移幂等（你的第 3 点）

### 1.1 读代码：现在的流程（`hooks/register.tsx:956-971`）

1. `model >= 2` 直接返回。
2. 先读现有点数 `cur`，再读 `legacyAffection`。有效数字就用它，否则用 `cur` 并写下来。
3. 由 `legacy` 算旧等级和目标点数 `THRESH[旧等级-1]`。
4. 再读一次现有点数 `now`，写入 `max(now, 目标)`，最后写 `model = 2`。

`max` 的对象是"目标"和"现有点数"，所以它**只会抬高、不会压低**：现有点数比目标高，保持不动；比目标低，抬到目标。

### 1.3 回答：会不会拉回手动改小的点数？

- 迁移完成后（`model = 2`）：**不会**（M2）。
- 迁移完成前：只有"读 `now`"到"写入"之间的几毫秒窗口，用户不可能在这段时间手改。
- 会拉回的是 M3 / M4：`model` 没有了（或小于 2），但 `legacyAffection` 还在。这时迁移会重新跑，并且**用旧原值而不是现在的点数**去算目标。
- 目前仓库里没有任何"重置存档"的操作（`hooks/register.tsx` 里没有 `store.delete`，也没有 reset 命令，我 grep 过）；`SECURITY.md:39` 写的重置办法是"删除整个存档文件"，这会把 `legacyAffection` 一起删掉，所以现在**没有现成的路径会触发**。

### P4-1（低，潜在）`legacyAffection` 永久保留、优先于现有点数

- **位置**：`hooks/register.tsx:962-969`
- **场景**：将来加一个"重置好感度"，如果只清 `affection`（或 `affection` + `model`）而没清 `legacyAffection`，下次启动会把点数抬回旧等级（M3 / M4）。手改存档只删 `model` 同理。
- **验证**：实际运行（M3、M4）。
- **建议**：约定"重置"= 写 `model: 2` 和 `affection: 0`（这样迁移永远不会再跑），或者三个键一起删。把这条写进 `SECURITY.md:39` 或 `CLAUDE.md`，免得以后忘。**不建议**在迁移完成后删 `legacyAffection`：另一个对话如果早先读到 `model` 还没写，就会读不到它，退回用已经抬过的 `cur`，等于重新引入重复抬升。

### P4-5（提示，推断）正确性依赖跨对话读写有序

- **位置**：`hooks/register.tsx:957-962` 一带的注释"先读点数、后读原值：看到抬过的点数的人，一定也看得到原值"。
- 这条推理要求：一个对话先写 `legacyAffection`、后写 `affection`，另一个对话**先**读到新的 `affection`，**后**读 `legacyAffection` 时一定能读到。这是 `$.store` 跨对话的读写顺序保证。测试环境只有一个对话，我**没法验证**，也没找到宿主对此的说明。
- 另外最后一步仍是"读 `now` → 写 `max`"，两步之间另一个对话如果恰好写了新点数会被覆盖，窗口只有一次 await，属于已知的 A-3 同类，我不再单独算一条。
- **你自己的存档**：迁移发生在 10 月 8 日的 v0.4.0（旧的、不幂等的版本），你的存档里没有 `legacyAffection`。如果当时有多个对话同时首启，点数可能被多抬过。这**从存档里查不出来**。如果你记得迁移前的旧等级，可以对照第三轮报告附录 A 的表（旧 Lv.N → 新点数）：现在的点数明显高于该表的"一次迁移"值，才说明被多抬过。

### P4-3（低）安慰计数不是原子的

- **位置**：`hooks/register.tsx:719-720`
  ```
  const comforting = (await reallyWorried($, now)) && !(await read($, moodComforted))
  if (comforting) await update($, moodComforted, () => true)
  ```
  "读标记 → 写标记"之间没有 `locked()`，而紧接着的 `takePatLocked` 是锁在里面的。
- **场景**：她担心时，两次摸头同时被派发（还没等第一次写完标记，第二次就读了标记）。
- **验证**【实际运行】：存档里 `comforts = 3`，制造一次出错使她担心，然后
  - 先后两次摸头（中间隔 3 秒）：计 1 次，`comforts = 4`，"贴心安慰"（要 5 次）**未**解锁（探针 C1）。
  - `Promise.all([摸头, 摸头])` 同时两次：计 2 次，`comforts = 5`，"贴心安慰"**已解锁**（探针 C2）。
  - 真实桌面端会不会把两次点击并发地送进模块，我**不知道**；人手快速双击间隔通常在 100 毫秒以上，而这段窗口只有几个 await，所以实际触发的可能性不大。
- **建议**：把"检查并标记"放进和 `takePatLocked` 同一个 `locked(...)` 里，或者先同步地写标记再 `await` 其他。后果只是多记一次安慰，故为低。
- **设计提示（不算问题）**：`feel('worried')` 每次都把标记重置（`:370`），所以她担心的 5 分钟内又出一次错，会算"新的一次担心"，可以再安慰一次。测试 `comfort: pats while she is worried count once per worry` 里"每次担心 3 次摸头"的写法就依赖这一点。这和"出错是真实事件、不能靠点击制造"的前提一致。
