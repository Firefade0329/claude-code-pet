## 2. 发现

### 中

#### N-1　迁移不是幂等的：几个对话同时首次启动时，存档可能被多抬几级（中）　【读代码 + 实际运行（算术、顺序情形）；并发为推断】

- 位置：`register.tsx:938-945`（`migrateModelLocked`）、`:947-950`（`restoreSaved` 在每个对话启动 30 毫秒后调用）。
- 问题：迁移先读 `model` 标记，没到 2 就读当前点数、按**旧**门槛算旧等级、写入 `max(点数, 新门槛[旧等级])`，最后写 `model = 2`。这个函数对"已经抬过的点数"再执行一次，会把它当旧存档再抬一次。`locked()` 只在一个对话里有效。
- 验证（实际运行）：
  - 用代码里的 `THRESH` 和旧公式，对每个旧等级算一次、两次、三次的结果：旧 Lv.1–8 重复执行不变；**旧 Lv.9 起每多执行一次就多一级**，例如旧 Lv.12（599 点）一次 741（Lv.12）、两次 866（Lv.13）、三次 1000（Lv.14）；旧 Lv.17（1176）一次 1451、两次 1618、三次 1975（Lv.20）。完整表见附录 A。
  - 顺序执行是安全的：我让真实插件从旧存档（1500 点，旧 Lv.19）启动，第一次 `session.start` 后 1792，第二次后仍是 1792（标记起了作用）。
  - 单次迁移不会掉级：0 到 2000 的每一个整数点数，单次迁移后的新等级都不低于旧等级（0 次掉级）。
- 并发为什么是推断：我没法在测试环境里开两个模块实例，所以不能证明两个对话会在彼此写入 `model` 之前都读到旧值；窗口是 4 次存档读写，Claude 桌面端重启并同时恢复几个对话时（代码里已有注释把这当真实场景，`:737` 附近）有可能发生。
- 损坏数据：`model` 缺失 / 损坏 → `num()` = 0 → 会再迁移一次（同样的多抬）；`affection` 损坏 → 0 → 迁移后写 0（没有比损坏更糟）。
- 影响：方向是多升，不掉级，但违反"只做一次"，且不可逆。
- 建议：让迁移**幂等**：第一次迁移时先把旧点数记成 `legacyAffection`（两个竞争者写的是同一个值），之后一律用 `legacyAffection` 算目标门槛 `max(当前点数, 新门槛[旧等级(legacyAffection)])`，这样重复执行结果相同；`legacyAffection` 存在就等于"已迁移"，不再单靠 `model`。顺序：先写 `legacyAffection`，再写 `affection`，最后写 `model`。

#### N-2　周六（或周日）只用一天会断连续天数（中）　【实际运行 + 读代码】

- 位置：`register.tsx:885`（`continuesStreak`）；`README.md:77`。
- 验证（实际运行）：真实插件，存档里 `streak.last` 分别设成周五 / 周六 / 周日，时钟设到周一，发第一条消息：周五 → 签到 7 点（连续继续）；**周六 → 3 点（断了）**；周日 → 7 点（继续）。模拟：周一到周五 → 400 天内最长连续 286；**周一到周五加周六、加周日、周一到周六 → 都是最长 6**。
- 影响：这几类用户永远拿不到 7 天以上的连续成就和"全部收集"；每次用了周末的一天，签到奖励从 8 掉回 3。周末两天都不用的人反而一直连续，激励是反的。
- 建议和伪代码见 `affection-model-v2-check-v0.5.0-2026-10-24.md` E-1：条件改成"上一次使用到今天之间缺的每一天都是周六或周日"。测试要补周六→周一、周五→周日。

#### N-3　窗口宽度启发式：内部一致，但只有一个数据点，而且几乎没有测试（低）　【读代码 + 实际运行；真实画面未验证】

- 位置：`register.tsx:89-96`、`:1367-1372`。
- 我验证了什么（实际运行）：①边界：`bodyColumns` 为 96 时右栏隐藏、97 时显示，与公式一致；②有"压缩上下文"按钮时（上下文 82%，不触发警告），109 列隐藏、110 列显示（= 97 + 13，13 = 按钮文字 10 格 + 3 格内边距和间隙），与公式一致；③常态按钮行的耗费 = 6 + 6 + 12 + 4 + 3×4 = 40，与 `ROW_BASE_COST = 40` 一致；④"今日"文字 `今日 14 轮·322 工具·0 番茄 ▸` 长度正好是 21，与 `SUM_LABEL_BASE = 21` 一致；⑤公式不会形成"窄→按钮挪进按钮行→按钮行变长→更窄"的反馈（`rowLabels` 不含这两个挪进来的按钮）。
- 问题：
  1. **测试几乎没有**：把 `NARROW_COLS` 改成 90、把两个动态项各自去掉、改 `SUM_LABEL_BASE` 或 `ROW_BASE_COST`，五个变异都没有测试失败（M19、M20、M21、M38、M39）。只有一个 60 列的窄窗口测试。
  2. **`rowLabels`（`:1368`）和真正渲染按钮的 `btnRow`（`:1376`）是两份手写的条件和文字**（例如 `放弃 · 剩${focusLeft}分` 写了两遍）。以后改了一边忘了另一边，阈值就会悄悄偏。
  3. **单位问题**：阈值是"格"，而小人（96 px）和进度条（262 px）的宽度是固定像素。`bodyColumns` 的文档只写"这块区域的宽度，单位是格，减去引擎自己占的 5 格"，没有写一格多少像素。所以"需要多少格"其实取决于一格的像素宽度（CHANGELOG 里量到约 9.7 px），宿主改字号、缩放、更新字体，阈值就会偏（这正是 0.4.1 那次事故的形态）。我无法在这里测，**推断**。
  4. `bodyColumns` 缺失时（旧版宿主）按"宽窗口"处理（我实际跑了：缺失 → 宽布局）；为 `null`/`NaN` 时按"窄窗口"处理（测试环境里序列化后变成 `null`，我实际跑了：窄布局）。
- 建议：①补五个阈值测试（我跑出来的边界值：96/97，109/110，见 `test-quality` §5）；②把 `rowLabels` 和 `btnRow` 用同一个"按钮列表"生成；③**给阈值开一个用户可调的选项**：`plugin.json` 的 `userConfig` 里加一个数字选项（比如 `narrowColumns`，默认 97），用户在 `/config` 里就能按自己的字号调整，不需要等你发新版（`PluginOptions` 的类型允许数字，**但 `userConfig` 里数字字段的写法我没有验证过**，我只验证过字符串字段）。

## 3. 心情系统的逐项检查【读代码 + 实际运行】
