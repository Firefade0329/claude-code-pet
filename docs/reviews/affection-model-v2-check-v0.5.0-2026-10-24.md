## 结论（先看这个）

1. **模拟本身可信：我让真实插件在测试环境里"用了 14 天"（每天 30 轮对话 + 5 次摸头），逐日读出界面上的好感度，和同一假设下的模拟逐日对比，14 天全部一致**（§2）。这一对照包含了每日签到、对话递减、摸头、成就奖励取整、升级这些环节。【实际运行】
2. **README / CHANGELOG 的天数：量级一致，但没写明假设，精确值取决于每天摸头几次和有没有番茄钟。** 在"摸头每天 3 次、没有番茄钟"下我复现了 8/30/60 和 15/53/109（README 写 8/30/59 和 15/53/106）；在"摸头每天 5 次"下是 7/28/56 和 12/50/101（§3）。偏差都在 ±10% 内。【实际运行（模拟）】
3. **上一轮指出的两个核心问题已经解决：**对话不再无限加分（每天 25 点封顶，每天 100 轮和每天 500 轮到满级的天数相同，都是 48 天）；满级最快也要约 39 天（每天 3 个番茄钟、满额），不再有"13 天满级"。【实际运行（模拟）】
4. **新问题：周六或周日"只用一天"会让连续天数断掉**（周五→周日、周六→周一都接不上），因此这类用户永远拿不到 7 天以上的连续成就。见 §4 E-1，这一条我认为该修。【实际运行（真实插件 + 模拟）】
5. 成就奖励总和 298 点，占满级 1975 点的 15.1%，到满级时实际到手 99–231 点（占来源的 5–12%）；仍然是"对升级影响很小"，这是设计选择，不是问题。

## 4. 发现

### 中

#### E-1　周末只用一天会断连续天数（中）　【实际运行（真实插件 + 模拟）】

- 位置：`register.tsx:885`（`continuesStreak`）。
- 复现：真实插件，存档里 `streak.last` 设成周五 / 周六 / 周日，时钟设到周一再发第一条消息：周五 → 签到 7 点（连续继续）；**周六 → 3 点（断了）**；周日 → 7 点（继续）。模拟：周一到周五 → 400 天内最长连续 286；周一到周五加周六 → 6；周一到周五加周日 → 6；周一到周六 → 6。
- 影响：这几类人永远拿不到"一周陪伴"（7 天）、"两周相伴"、"满月之约"、"百日相伴"和"全部收集"（合计原始奖励 41 + 10 点，各自 ×1.3 取整后共 67 点）；而周末两天都不用的人反而不断。
- 建议（伪代码）：连续的条件改成"上一次使用到今天之间缺的每一天都是周六或周日"：

```
function continues(last, today):
    d = dayAfter(last)
    while d < today:
        if weekday(d) not in (Saturday, Sunday): return false
        d = dayAfter(d)
    return true        // last 就是昨天时，循环不执行，直接 true
```

  这会让周五→周日（缺周六）、周六→周一（缺周日）、周五→周一（缺周六日）都连续，周四→周一不连续（缺周五）。测试需要补：周六→周一、周五→周日。

#### E-2　迁移在几个对话同时首次启动时会多抬几级（中）　【算术（实际运行 node）+ 顺序情形（实际运行）；并发为推断】

- 位置：`register.tsx:938-945`（`migrateModelLocked`），由 `restoreSaved`（`:947`）在每个对话启动 30 毫秒后调用。
- 问题：迁移是"读 `model` 标记 → 读旧点数 → 按旧门槛算旧等级 → 写 `max(旧点数, 新门槛[旧等级])` → 写 `model = 2`"。顺序执行时标记保证只做一次（我实际跑了：旧 Lv.19 的 1500 点，第一次 `session.start` 后是 1792，第二次后仍是 1792）。但这个函数**本身不是幂等的**：对已经抬过的点数再做一次，会把它当作旧存档再抬一级。我用原代码的算术跑了每个旧等级：旧 Lv.1–8 重复做不变；**旧 Lv.9 起，每多做一次就多一级**：例如旧 Lv.12（599）→ 741（新 Lv.12）→ 866（Lv.13）→ 1000（Lv.14）；旧 Lv.17（1176）一次 → 1451，两次 → 1618，三次 → 1975（Lv.20）。
- 触发条件：`locked()` 只在一个对话里有效。几个对话同时首次启动（比如 Claude 桌面端重启，同时恢复几个对话；代码注释 `:737` 附近自己就把这当作真实场景）时，它们都可能在彼此写入 `model` 之前读到旧标记。时间窗口是 4 次存档读写，我没法在测试环境里复现真并发，所以"会不会发生"是**推断**。
- 影响：方向是**多升**，不会掉级；但会违背"一次性迁移"的说明，并且数字不可逆。
- 建议：让迁移**幂等**。办法：第一次迁移时把"旧点数"记下来（写一个 `legacyAffection`，两个竞争者写的是同一个值），之后每次都用 `legacyAffection` 算目标门槛，而不是用当前点数算；这样重复执行结果相同。顺序是先写 `legacyAffection` 再写 `affection` 再写 `model`。同时让缺失 / 损坏的 `model` 标记不会触发重复迁移（`legacyAffection` 存在就算已经迁移）。

### 低

#### E-3　轻度用户要 8–9 个月才到满级，家人阶段要 4 个多月（低）　【实际运行（模拟）；是否合适是设计判断】
- 轻度（每周 4 天、每天 5 轮）：Lv.7 第 33 天、Lv.14 第 131 天、Lv.20 第 263 天。上一轮 B-3 提过"家人阶段对轻度用户很远"，v2 里这一点没变（略慢了一点）。如果希望轻度用户也能看到家人阶段，Lv.14 的门槛或签到奖励需要调；如果这是有意的"长期陪伴"，可以不改。

#### E-4　摸头相关成就仍然可以连点刷出来，新的"贴心安慰"也一样（低）　【读代码 + 读测试】
- 位置：`register.tsx:718-726`（摸头超过每天 5 次后，仍然 `bumpStats({ pats: 1, comforts: … })`）。
- 问题：`pat50 / pat200 / pat500` 和隐藏成就 `comfort`（"她担心的时候摸摸头 5 次"）都按点击次数计，不受每天 5 次的限制；一次出错后的 5 分钟内连点 5 下就能拿到"贴心安慰"。`pet.test.ts` 里的 comfort 测试走的正是"第 6 到第 10 次摸头（不计分）也计 comfort"这条路径，所以这是被测试固定下来的行为，可能是有意的。
- 建议：如果不是有意的，让 `comforts` 也只计"计分的那几次"；或者给点击加最短间隔。

#### E-5　"满级时已解锁成就数"在 19–35/41 之间，满级后还有大量奖励拿不到价值（低）　【实际运行（模拟）】
- 到满级时模拟里已解锁 19/41（轻度）～ 35/41（重度 + 番茄钟）；没拿到的奖励在满级后就没有用了。这和上一轮 B-2 同类：成就奖励总和占满级点数的 15.1%，满级时实际到手 5–12%（占总和的三分之一到八成不等），其余要在满级后才拿得到。属于设计取舍，不一定要改。

## 5. 需要维护者回答的问题

1. 周末规则的本意是哪一种（见 E-1）：只放过"周五到周一"的整个周末，还是"周六、周日可以不用，用了也不影响"？
2. README 里"约 8 天 / 30 天 / 59 天"的假设是什么（摸头几次、有没有番茄钟）？我能复现的是摸头 3 次/天。
3. 迁移的并发窗口你觉得有可能发生吗？（你自己的存档是不是只有一个对话在首次启动时跑迁移？）要不要按 E-2 的办法改成幂等？
4. `comforts` 和 `pat*` 成就计不计分的那几次，是有意让它们不受每天 5 次限制吗？
5. 轻度用户要 8–9 个月才满级，这是想要的吗？
